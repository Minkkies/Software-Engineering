# สรุปเนื้อหา: Project Management (การบริหารโครงการซอฟต์แวร์)
---

## 1. หลัก 4 P's ของการบริหารโครงการ

| P | ความหมาย |
|---|----------|
| **People** (บุคลากร) | องค์ประกอบที่สำคัญที่สุดต่อความสำเร็จของโครงการ |
| **Product** (ผลิตภัณฑ์) | ซอฟต์แวร์ที่ต้องสร้าง |
| **Process** (กระบวนการ) | กรอบกิจกรรมและงานวิศวกรรมซอฟต์แวร์ที่ใช้ทำงานให้สำเร็จ |
| **Project** (โครงการ) | งานทั้งหมดที่จำเป็นเพื่อทำให้ผลิตภัณฑ์เกิดขึ้นจริง |

---

## 2. People: ทีมซอฟต์แวร์

**คำถามหลักของการบริหารทีม:** จะนำทีมอย่างไร? จัดโครงสร้างอย่างไร? สร้างแรงจูงใจอย่างไร? ทำงานร่วมกันอย่างไร? สร้างไอเดียที่ดีอย่างไร?

**ปัจจัยที่ต้องพิจารณาเมื่อเลือกโครงสร้างทีม**
- ความยากของปัญหา
- ขนาดของโปรแกรม (จำนวนบรรทัดโค้ด หรือ function points)
- ระยะเวลาที่ทีมจะอยู่ด้วยกัน (team lifetime)
- ระดับที่ปัญหาสามารถแบ่งเป็นโมดูลได้
- คุณภาพและความน่าเชื่อถือของระบบที่ต้องการ
- ความเข้มงวดของวันส่งมอบ
- ระดับการสื่อสารระหว่างสมาชิกที่โครงการต้องการ

---

## 3. Product: ขอบเขตของผลิตภัณฑ์ (Scope)

ขอบเขตต้องตอบ 3 เรื่อง:

1. **Context (บริบท):** ซอฟต์แวร์เข้าไปอยู่ในระบบ/ผลิตภัณฑ์/ธุรกิจที่ใหญ่กว่าอย่างไร และมีข้อจำกัดอะไรจากบริบทนั้น
2. **Information objectives (วัตถุประสงค์ด้านข้อมูล):** ข้อมูลที่ลูกค้าเห็นเป็นผลลัพธ์คืออะไร และต้องใช้ข้อมูลนำเข้าอะไร
3. **Function and performance (หน้าที่และสมรรถนะ):** ซอฟต์แวร์แปลงอินพุตเป็นเอาต์พุตอย่างไร และมีข้อกำหนดด้านประสิทธิภาพพิเศษหรือไม่

**หลักสำคัญ:** ขอบเขตต้อง *ชัดเจน ไม่กำกวม* และเข้าใจได้ทั้งในระดับผู้บริหารและระดับเทคนิค

---

## 4. Process: กระบวนการ

เมื่อกำหนดกรอบกระบวนการ (process framework) แล้ว ให้:
1. พิจารณาลักษณะเฉพาะของโครงการ
2. กำหนดระดับความเข้มงวด (rigor) ที่ต้องใช้
3. กำหนด **Task set** ของแต่ละกิจกรรมวิศวกรรมซอฟต์แวร์

**Task set ประกอบด้วย:** งานวิศวกรรมซอฟต์แวร์ + ผลงานที่ส่งมอบ (work products) + จุดประกันคุณภาพ (QA points) + หลักไมล์ (milestones)

**Melding the Problem and the Process (Figure 21.2):** นำ "หน้าที่ของผลิตภัณฑ์" (เช่น text input, editing/formatting, automatic copy edit, page layout, automatic indexing/TOC, file management, document production) มาทำเป็นตารางเทียบกับ "กิจกรรมของกระบวนการ" (communication, planning, modeling, construction) เพื่อวางแผนงานให้ครอบคลุมทุกช่อง

---

## 5. Project: โครงการคืออะไร

- **โครงการ** คือกิจกรรมที่มีการวางแผน
- **โครงการ SE** คือโครงการที่มีส่วนประกอบซอฟต์แวร์เป็นสาระสำคัญ (และพบมากขึ้นเรื่อย ๆ)

### โครงการมีปัญหาเมื่อ…
- ทีมไม่เข้าใจความต้องการของลูกค้า
- ขอบเขตผลิตภัณฑ์ไม่ชัดเจน
- จัดการการเปลี่ยนแปลงไม่ดี
- เทคโนโลยีที่เลือกใช้เปลี่ยนไป
- ความต้องการทางธุรกิจเปลี่ยนหรือไม่ชัดเจน
- กำหนดเวลาไม่สมเหตุสมผล
- ผู้ใช้ต่อต้าน
- ขาดผู้สนับสนุน (sponsor)
- ทีมขาดคนที่มีทักษะเหมาะสม
- ผู้บริหารและผู้ปฏิบัติงานเลี่ยง best practices และบทเรียนที่เคยได้

### นิยามการบริหารโครงการ
การประยุกต์ใช้ความรู้ ทักษะ เครื่องมือ และเทคนิค กับกิจกรรมของโครงการ เพื่อให้ตอบสนองหรือเกินความคาดหวังของผู้มีส่วนได้ส่วนเสีย (stakeholders)

---

## 6. กิจกรรมการบริหาร (Management Activities)

ระดับการมีส่วนร่วมในแต่ละกิจกรรมขึ้นอยู่กับระดับอาวุโสของผู้จัดการ

| กิจกรรม | สาระสำคัญ |
|---------|-----------|
| **Proposal writing** (เขียนข้อเสนอ) | ระบุว่าจะทำอะไร ทำอย่างไร เมื่อไร ราคาเท่าไร และผู้รับเหมาต้องแสดงเหตุผลว่าทำไมจึงมีคุณสมบัติเหมาะสม |
| **Project costing** (ประเมินต้นทุน) | ประเมินต้นทุนรวมของโครงการ ฝั่งลูกค้าต้องแลกระหว่างต้นทุนกับข้อกำหนด (ปัจจัยองค์กร/การเมืองมีผลมาก) ฝั่งผู้รับเหมาหลัก ๆ คือต้นทุนฮาร์ดแวร์ + บุคลากร |
| **Planning & scheduling** (วางแผนและกำหนดตาราง) | ประเมินแรงงาน จัดกิจกรรม และจัดสรรบุคลากร ซับซ้อนมากในโครงการใหญ่ที่มีผู้รับเหมาช่วงหลายราย |
| **Monitoring & reviews** (ติดตามและทบทวน) | ตรวจว่าเป็นไปตามมาตรฐานคุณภาพและแผนหรือไม่ ผลที่ได้ป้อนกลับไปปรับแผน การทบทวนโครงการคือการประชุมทางการเพื่อตัดสินใจเปลี่ยนแปลงแผน |
| **Personnel selection** (คัดเลือกบุคลากร) | กำหนดทักษะที่ต้องใช้และมอบหมายคน ต้องมีทักษะผสมกัน โครงการที่มีแต่ผู้เชี่ยวชาญเทคนิคล้วน ๆ มักไม่สำเร็จ |
| **Reports & presentations** (รายงานและนำเสนอ) | เขียนรายงานความคืบหน้า การตอบสนองต่อคำขอเปลี่ยนแปลง ปัญหาที่เกิดขึ้น ต้องชัดเจนและกระชับ เพราะผู้อ่านไม่มีเวลาอ่านเอกสารยาว |

## 7. ทำไมโครงการจึงล่าช้า (Why Are Projects Late?)

1. กำหนดเวลาไม่สมเหตุสมผลโดยคนนอกทีมพัฒนา
2. ความต้องการลูกค้าเปลี่ยนแต่ไม่ได้ปรับตาราง
3. ประเมินแรงงาน/ทรัพยากรต่ำเกินไปโดยสุจริต
4. ความเสี่ยงที่คาดได้หรือคาดไม่ได้ ซึ่งไม่ได้นำมาพิจารณาตั้งแต่ต้น
5. ปัญหาทางเทคนิคที่เห็นล่วงหน้าไม่ได้
6. ปัญหาด้านมนุษย์ที่เห็นล่วงหน้าไม่ได้
7. การสื่อสารระหว่างทีมผิดพลาด
8. ผู้บริหารโครงการไม่รู้ตัวว่าโครงการกำลังล้าหลัง และไม่แก้ไข

## 8. การวางแผนโครงการ (Project Planning)

- เป็นกิจกรรมที่ **ใช้เวลามากที่สุด** ของการบริหารโครงการ
- ทำต่อเนื่องตั้งแต่แนวคิดเริ่มต้นจนส่งมอบระบบ และต้องปรับแผนเมื่อมีข้อมูลใหม่
- แผนหลักระบุ: กิจกรรม ทรัพยากรที่ต้องใช้ ความสัมพันธ์ระหว่างกิจกรรม และเวลาที่ต้องใช้

### สิ่งที่แผนต้องจัดการ
- **ทรัพยากรที่มี**
- **การจัดตารางทรัพยากร** (บางทรัพยากรใช้ได้หลายกิจกรรม บางอย่างไม่ได้)
- **Work breakdown:** แตกงานเป็นเป้าหมายและงานย่อย แล้วแตกต่อได้อีก
- **ตารางงาน** ที่คำนึงถึงทรัพยากร บุคลากร และเวลา (การวิเคราะห์ *ความสัมพันธ์พึ่งพาของงาน* เป็นหัวใจของการวางแผน)

### กระบวนการวางแผน (Pseudocode ในสไลด์)
```
กำหนดข้อจำกัดของโครงการ
ประเมินพารามิเตอร์เบื้องต้น
กำหนด milestones และ deliverables

while (โครงการยังไม่เสร็จหรือถูกยกเลิก) {
    ร่างตารางงาน
    เริ่มกิจกรรมตามตาราง
    รอสักระยะ
    ทบทวนความคืบหน้า
    ปรับประมาณการพารามิเตอร์
    อัปเดตตารางงาน
    เจรจาข้อจำกัดและ deliverables ใหม่
    if (เกิดปัญหา) → ทบทวนเทคนิคและแก้ไขถ้าจำเป็น
}
```

### โครงสร้างเอกสารแผนโครงการ
1. Introduction (บทนำ)
2. Project organization (โครงสร้างองค์กรโครงการ)
3. Risk analysis (วิเคราะห์ความเสี่ยง)
4. Hardware and software resource requirements (ทรัพยากรฮาร์ดแวร์/ซอฟต์แวร์)
5. Work breakdown (การแบ่งงาน)
6. Project schedule (ตารางโครงการ)
7. Monitoring and reporting mechanisms (กลไกติดตามและรายงาน)

## 9. การจัดระเบียบกิจกรรม: Milestones และ Deliverables

| คำศัพท์ | ความหมาย |
|---------|----------|
| **Milestone** | จุดสิ้นสุดของกิจกรรมในกระบวนการ ใช้ให้ฝ่ายบริหารตัดสินความคืบหน้า |
| **Deliverable** | ผลงานของโครงการที่ **ส่งมอบให้ลูกค้า** |

กิจกรรมควรสร้างผลลัพธ์ที่จับต้องได้ และโมเดล Waterfall ช่วยให้กำหนด milestone ได้ตรงไปตรงมา

**ตัวอย่างจากสไลด์ (กิจกรรม → milestone):**
- Feasibility study → Feasibility report
- Requirements analysis → Requirements specification
- Design study → Architectural design
- Prototype development → Evaluation report

## 10. การจัดตารางโครงการ (Project Scheduling)

**เป้าหมาย:** แบ่งโครงการเป็นงาน และประเมินเวลา/ทรัพยากรของแต่ละงาน

**แนวทาง**
- จัดงานให้ทำ *ขนานกัน* เพื่อใช้แรงงานให้คุ้มที่สุด
- ลดความพึ่งพาระหว่างงาน เพื่อไม่ให้งานหนึ่งล่าช้าแล้วลากงานอื่นล่าช้าตาม
- การจัดตารางขึ้นกับสัญชาตญาณและประสบการณ์ของผู้จัดการโครงการมาก

### หลักการจัดตาราง (Scheduling Principles)
1. **Compartmentalization:** นิยามงานให้แยกกันชัดเจน
2. **Interdependency:** ระบุความสัมพันธ์ระหว่างงาน
3. **Effort validation:** ตรวจว่ามีทรัพยากรเพียงพอ
4. **Defined responsibilities:** มอบหมายคนรับผิดชอบ
5. **Defined outcomes:** ทุกงานต้องมีผลลัพธ์
6. **Defined milestones:** มีจุดทบทวนคุณภาพ

### การกระจายแรงงาน (Effort Allocation)

| ช่วงงาน | สัดส่วน |
|---------|---------|
| Front end: สื่อสารกับลูกค้า, วิเคราะห์, ออกแบบ, ทบทวนและแก้ไข | **40–50%** |
| Construction: เขียนโค้ดหรือสร้างโค้ดอัตโนมัติ | **15–20%** |
| Testing & installation: unit, integration, white-box, black-box, regression | **30–40%** |

### กระบวนการจัดตาราง
`ระบุกิจกรรม` → `ระบุความสัมพันธ์ของกิจกรรม` → `ประเมินทรัพยากร` → `จัดคนเข้ากิจกรรม` → `สร้างแผนภูมิโครงการ`
(อินพุตคือ Software requirements และเอาต์พุตคือ Activity charts และ Bar charts โดยมีการวนย้อนกลับเพื่อปรับปรุง)

### Bar chart และ Activity network
- **Activity chart (activity network):** แสดงความพึ่งพาของงานและ *critical path*
- **Bar chart:** แสดงตารางเทียบกับเวลาตามปฏิทิน
- โครงการใหญ่ต้องมีหลายระดับ: ระดับบนงานอาจใช้เวลาหลายเดือนหรือหลายปี ส่วนระดับละเอียดสุด งานควรยาว **1–2 สัปดาห์**

## 12. สรุปสั้น ๆ สำหรับทบทวนก่อนสอบ

- **4 P's** = People, Product, Process, Project โดย *People สำคัญที่สุด*
- ขอบเขตผลิตภัณฑ์ = Context + Information objectives + Function/Performance และต้องไม่กำกวม
- โครงการล้มเหลวมักเพราะ: ไม่เข้าใจความต้องการ ขอบเขตไม่ชัด จัดการการเปลี่ยนแปลงไม่ดี เวลาไม่สมเหตุสมผล ขาดคนเก่ง
- การวางแผนเป็น **กิจกรรมต่อเนื่อง** ต้องทบทวนและปรับแผนเสมอ
- **Milestone** = จุดจบของกิจกรรม / **Deliverable** = สิ่งที่ส่งมอบลูกค้า
- แรงงานโดยประมาณ: **40–50% front end, 15–20% coding, 30–40% testing**
- **Critical path** = เส้นทางที่ยาวที่สุดในเครือข่ายกิจกรรม งานบนเส้นนี้ล่าช้า = โครงการล่าช้า
