# บทที่ 1: ซอฟต์แวร์คืออะไร และวิศวกรรมซอฟต์แวร์คืออะไร

## 1.1 ซอฟต์แวร์คืออะไร?

ให้นึกภาพว่าซอฟต์แวร์ไม่ใช่แค่ "โปรแกรม" อย่างเดียว แต่เป็น **ชุดของสิ่งของ (configuration)** ที่ประกอบด้วย 3 ส่วนหลัก:
- **โปรแกรม (programs)** — ตัวโค้ดที่รันได้
- **เอกสาร (documents)** — คู่มือ, สเปค, แบบออกแบบ
- **ข้อมูล (data)** — ข้อมูลที่โปรแกรมใช้งาน

> **ตัวอย่าง:** แอปธนาคารบนมือถือ ไม่ได้มีแค่โค้ด แต่มีคู่มือการใช้งาน มีฐานข้อมูลลูกค้า และมีเอกสารสเปคที่บอกว่าระบบต้องทำอะไรได้บ้าง — ทั้งหมดนี้รวมกันคือ "ซอฟต์แวร์"

## 1.2 บทบาทคู่ของซอฟต์แวร์ (Software's Dual Role)

1. **ซอฟต์แวร์เป็นผลิตภัณฑ์ (a product)** — ส่งมอบศักยภาพการประมวลผลให้ผู้ใช้ เช่น แอปคำนวณเงินเดือน
2. **ซอฟต์แวร์เป็นพาหนะนำส่งผลิตภัณฑ์อื่น (a vehicle)** — เช่น ระบบปฏิบัติการ (OS) ที่ควบคุมโปรแกรมอื่น หรือซอฟต์แวร์เครือข่ายที่ทำให้อุปกรณ์สื่อสารกันได้

## 1.3 ตัวอย่างความล้มเหลวของวิศวกรรมซอฟต์แวร์

| เหตุการณ์ | ปัญหา |
|---|---|
| Year 1900 Bug (1992) | ระบบคำนวณอายุผิดพลาด ทำให้ผู้หญิงอายุ 104 ปี ได้รับจดหมายเชิญไปเรียนอนุบาล |
| สนามบิน Denver (1995) | ระบบสายพานกระเป๋าอัตโนมัติมีบั๊ก ทำให้กระเป๋าเสียหาย เปิดสนามบินช้ากว่ากำหนด 16 เดือน และงบบานปลายมหาศาล |
| ระบบประกันสุขภาพ Wisconsin (1984) | ระบบมูลค่า 200 ล้านดอลลาร์ทำงานผิดพลาด จ่ายเงินเกินไป 60 ล้านดอลลาร์ ต้องใช้เวลาแก้ไข 3 ปี |

**บทเรียน:** ความผิดพลาดเล็กๆ ในซอฟต์แวร์สามารถสร้างความเสียหายมหาศาลได้ นี่คือเหตุผลที่เราต้องมีกระบวนการที่เป็นระบบ

## 1.4 ธรรมชาติของซอฟต์แวร์

- **จับต้องไม่ได้ (intangible)** — วัดความคืบหน้าการพัฒนายาก
- **ทำซ้ำได้ง่าย (easy to reproduce)** — ต้นทุนอยู่ที่การพัฒนา ไม่ใช่การผลิต (ต่างจากวิศวกรรมอื่นที่ต้นทุนอยู่ที่การผลิต/manufacturing)
- **เป็นงานที่ใช้แรงงานเข้มข้น (labor-intensive)** — ทำให้อัตโนมัติได้ยาก
- **แก้ไขง่าย** — แต่คนมักแก้โดยไม่เข้าใจทั้งระบบ ทำให้เกิดปัญหาใหม่
- **ไม่ "สึกหรอ" (does not wear out)** แต่ **"เสื่อมสภาพ" (deteriorates)** จากการถูกแก้ไขซ้ำๆ โดยไม่ได้ตั้งใจหรือไม่ได้คาดคิดไว้ ทำให้ซับซ้อนขึ้นเรื่อยๆ

> **ตัวอย่างเปรียบเทียบ:** รถยนต์สึกหรอเพราะชิ้นส่วนเสียดสีกันตามเวลา แต่ซอฟต์แวร์ไม่ได้ "สึก" แบบนั้น — มันแย่ลงเพราะทุกครั้งที่มีคนมาแก้บั๊กหรือเพิ่มฟีเจอร์แบบเร่งรีบ โดยไม่เข้าใจโค้ดเดิมทั้งหมด อัตราการเกิดข้อผิดพลาด (failure rate) จะสูงขึ้นเรื่อยๆ ต่างจากเส้นโค้งในอุดมคติ (idealized curve)

## 1.5 ตำนาน (Myths) เกี่ยวกับซอฟต์แวร์

| ตำนาน (Myth) | ความจริง (Reality) |
|---|---|
| ถ้าโปรเจกต์ล่าช้า เพิ่มคนเข้าไปก็จะทันเวลา | การเพิ่มคนกลางโปรเจกต์ทำให้ **ช้าลงกว่าเดิม** เพราะคนเก่าต้องเสียเวลาสอนงานคนใหม่ (กฎของ Brooks) |
| แค่บอกวัตถุประสงค์กว้างๆ ก็เริ่มเขียนโปรแกรมได้เลย รายละเอียดค่อยเติมทีหลัง | การนิยามความต้องการที่ไม่ดีตั้งแต่แรกคือสาเหตุหลักของโปรเจกต์ที่ล้มเหลว |
| เขียนโปรแกรมเสร็จ ทดสอบผ่าน ก็จบงานแล้ว | จริงๆ แล้ว **60-80%** ของความพยายามทั้งหมดเกิดขึ้น **หลัง** จากส่งมอบซอฟต์แวร์ (ช่วงบำรุงรักษา/maintenance) |

## 1.6 วิศวกรรมซอฟต์แวร์คืออะไร?

> วิศวกรรมซอฟต์แวร์ คือ ศาสตร์ที่ทีมงานนำไปใช้เพื่อผลิตซอฟต์แวร์คุณภาพสูง ขนาดใหญ่ คุ้มค่า ตอบโจทย์ผู้ใช้ และดูแลรักษาต่อได้ในระยะยาว

องค์ประกอบที่หลอมรวมกันเป็นวิศวกรรมซอฟต์แวร์:
- **ทฤษฎี (theory)** จาก computer science
- **แนวทาง/วิธีการ (guidelines and methods)**
- **ประสบการณ์วิชาชีพ (professional experience)** — ยังคงเป็น "ศิลปะ" (craft) อยู่บ้าง
- **การบริหารโครงการ (project management)**
- ศาสตร์อื่นๆ ที่เกี่ยวข้อง

เป้าหมายสุดท้าย: ได้ **ระบบคอมพิวเตอร์ที่ทำงานในสภาพแวดล้อมจริง บรรลุเป้าหมาย ภายใต้งบประมาณที่กำหนด**

## 1.7 แนวปฏิบัติ (Practice) ตาม 5 ขั้นตอนหลักของกระบวนการ

Practice คือรายละเอียดเชิงเทคนิคที่อยู่ "ใต้ผิวน้ำ" ของกระบวนการ (process) แบ่งตามกิจกรรมหลัก:

1. **Communication (การสื่อสาร)** — ฟังให้มาก, เตรียมตัวก่อนคุย, พบหน้ากันดีที่สุด, จดบันทึกการตัดสินใจ, การเจรจาที่ดีคือ win-win ทั้งสองฝ่าย
2. **Planning (การวางแผน)** — เข้าใจขอบเขตโครงการ, ให้ลูกค้ามีส่วนร่วม, วางแผนแบบวนซ้ำได้ (iterative), ประเมินความเสี่ยง
3. **Modeling (การสร้างแบบจำลอง)** — สร้าง **Analysis model** (มุมมองความต้องการ: ข้อมูล/ฟังก์ชัน/พฤติกรรม) และ **Design model** (สถาปัตยกรรม, UI, รายละเอียดคอมโพเนนต์)
4. **Construction (การสร้างจริง)** — ก่อนเขียนโค้ด: ต้องเข้าใจปัญหา, เลือกภาษาที่เหมาะสม, เตรียม unit test; ระหว่างเขียน: ตั้งชื่อตัวแปรให้สื่อความหมาย, เขียนโค้ดที่อธิบายตัวเองได้ (self-documenting); หลังเขียน: ทำ code walkthrough, refactor
5. **Deployment (การส่งมอบ)** — จัดการความคาดหวังของลูกค้า, เตรียมเอกสารผู้ใช้, แก้บั๊กก่อนส่งมอบฟีเจอร์ใหม่

> **ตัวอย่าง:** ตอนพัฒนาแอปสั่งอาหาร ทีมต้อง **Communication** กับร้านอาหารและลูกค้าก่อนว่าต้องการอะไร แล้ว **Planning** ว่าจะทำฟีเจอร์ไหนก่อนหลัง จากนั้น **Modeling** ว่าระบบจะมีข้อมูลอะไรบ้าง (เมนู, ออเดอร์, ผู้ใช้) แล้วค่อย **Construction** เขียนโค้ดจริง และสุดท้าย **Deployment** ปล่อยแอปให้ใช้งานจริง พร้อมคู่มือ

## 1.8 บทบาทของ AI กับวิศวกรรมซอฟต์แวร์

สไลด์สรุป 5 บทบาทหลักที่ AI เข้ามาช่วยงานวิศวกรรมซอฟต์แวร์ในปัจจุบัน:

1. **ผู้ช่วยเขียนโค้ด (AI Coding Assistance)** — เป็นเหมือน "คู่หูเขียนโค้ด" (pair programmer) วิเคราะห์บริบทและแนะนำโค้ดแบบเรียลไทม์ เช่น GitHub Copilot หรือ Claude จาก Anthropic
2. **ตรวจหาและแก้บั๊ก (Bug Detection & Debugging)** — สแกนหาช่องโหว่ด้านความปลอดภัยก่อนใช้งานจริง เช่น GitHub Advanced Security ตรวจจับความเสี่ยงอย่าง SQL Injection
3. **ทดสอบซอฟต์แวร์อัตโนมัติ (Automated Testing)** — ช่วยสร้าง test case และข้อมูลจำลอง เช่น testRigor หรือ Applitools ที่เขียนเทสต์ด้วยภาษามนุษย์ทั่วไป
4. **บริหารจัดการโปรเจกต์ (Project Management & Planning)** — วิเคราะห์ข้อมูลย้อนหลังเพื่อประเมินเวลาและความเสี่ยง เช่น Jira ใช้ AI ช่วยคาดการณ์ความล่าช้า
5. **ดูแลระบบหลังใช้งานจริง (Maintenance & Operations)** — ตรวจจับความผิดปกติแบบเรียลไทม์ในสาย DevOps เช่น Datadog หรือ AWS DevOps Guru

## สรุปจำง่าย

- ซอฟต์แวร์คือทั้งโปรแกรม เอกสาร และข้อมูล
- เหตุผลที่ต้องมี SE เพราะซอฟต์แวร์ซับซ้อนและผิดพลาดได้แพง
- กระบวนการหลักเริ่มจากสื่อสาร วางแผน สร้างแบบจำลอง สร้างจริง และส่งมอบ
- AI เข้ามาช่วยได้ทั้งเขียนโค้ด ตรวจบั๊ก ทดสอบ วางแผน และดูแลระบบ
