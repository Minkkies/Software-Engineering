# บทที่ 2: วงจรชีวิตการพัฒนาซอฟต์แวร์ และแบบจำลองกระบวนการ (SDLC & Process Models)

## 2.1 แนวคิดพื้นฐาน: Process vs Product

- **Process (กระบวนการ)** = ชุดของขั้นตอนที่คาดเดาได้ ใช้เป็น "แผนที่" นำทางไปสู่ผลิตภัณฑ์คุณภาพสูงและตรงเวลา
- **Product (ผลิตภัณฑ์)** = สิ่งที่ได้ออกมา เช่น โปรแกรม เอกสาร และข้อมูล

> คิดง่ายๆ: **Process คือ "สูตรอาหาร"** ส่วน **Product คือ "จานอาหารที่เสิร์ฟ"**

## 2.2 วงจรชีวิตซอฟต์แวร์ (SDLC) แบบดั้งเดิม

สไลด์แสดง 2 เวอร์ชันของขั้นตอน SDLC:
- แบบที่ 1: Problem Definition → Analysis → Design → Development → Testing → Implementation → Maintenance
- แบบที่ 2 (ย่อ): Planning → Analysis → Design → Implementation → Support

## 2.3 คุณภาพซอฟต์แวร์ (Software Quality)

- **Quality of Design (คุณภาพการออกแบบ)** — วัดว่าการออกแบบและความต้องการนั้น "ดี/ถูกต้อง" แค่ไหน
- **Quality of Conformance (คุณภาพความสอดคล้อง)** — วัดว่าซอฟต์แวร์ที่สร้างขึ้นจริง **ตรงกับ** การออกแบบที่วางไว้แค่ไหน

> **ตัวอย่าง:** ถ้าออกแบบระบบเข้าสู่ระบบให้รองรับ 2FA (design ดี) แต่โปรแกรมเมอร์ลืมใส่ 2FA ตอนเขียนโค้ด (conformance แย่) — นี่คือปัญหาคุณภาพด้าน conformance

## 2.4 แบบจำลองกระบวนการเชิงพรรณนา (Prescriptive Process Models)

### ก) Waterfall Model (แบบน้ำตก)
ขั้นตอนไหลลงมาเป็นเส้นตรง: **Communication → Planning → Modeling → Construction → Deployment**

- **ข้อดี:** เรียบง่าย ทำตามขั้นตอนได้ง่าย
- **ข้อเสีย:** ไม่ยืดหยุ่น (โครงการจริงไม่ค่อยไหลเป็นเส้นตรงแบบนี้), ลูกค้าต้องรอจนถึงช่วงท้ายถึงจะเห็นระบบจริง, ลูกค้ามีส่วนร่วมแค่ตอนต้น

> **ตัวอย่าง:** เหมาะกับโครงการที่ความต้องการชัดเจนมากตั้งแต่แรก เช่น ระบบควบคุมของหน่วยงานราชการที่มีสเปคตายตัว ไม่ค่อยเปลี่ยนกลางทาง

### ข) Prototyping Model (แบบต้นแบบ)
ขั้นตอน: รวบรวมความต้องการ → ออกแบบเร็วๆ (quick design) → สร้างต้นแบบ → ให้ลูกค้าทดลองใช้ → วนกลับไปเริ่มใหม่

- **ข้อดี:** ระบุความต้องการได้เร็ว, ลูกค้าเห็นและให้ฟีดแบ็กได้เร็ว, เหมาะกับกรณีที่ลูกค้าบอกความต้องการละเอียดไม่ได้ หรือใช้เทคโนโลยีใหม่
- **ข้อเสีย:** นักพัฒนามักเผลอเอา prototype ไปทำเป็นระบบจริงเลย (ทั้งที่ควรจะทิ้งแล้วสร้างใหม่ให้ดี) ทำให้คุณภาพไม่ดี

> **ตัวอย่าง:** การออกแบบหน้าตาแอป (UI) ให้ลูกค้าดูก่อนว่า "ประมาณนี้ใช่ไหม" ก่อนจะไปเขียนโค้ดจริงทั้งระบบ

### ค) Incremental Model (แบบส่วนเพิ่ม)
รวมแนวคิดของ waterfall (เป็นเส้นตรง) กับ prototyping (ทำซ้ำเป็นรอบ) เข้าด้วยกัน โดยส่งมอบ **ผลิตภัณฑ์ที่ใช้งานได้จริง** ทีละส่วน (increment) เริ่มจาก core product ก่อน

> **ตัวอย่าง:** แอป e-commerce เวอร์ชันแรกส่งมอบแค่ระบบดูสินค้ากับตะกร้า (increment 1) เวอร์ชันต่อมาค่อยเพิ่มระบบชำระเงิน (increment 2) แล้วค่อยเพิ่มระบบรีวิวสินค้า (increment 3) — เหมาะเมื่อกำลังคนไม่พอจะทำทีเดียวจบ

### ง) RAD Model (Rapid Application Development)
เป็นเวอร์ชัน "ความเร็วสูง" ของ linear model ใช้การพัฒนาแบบ component-based โดยแบ่งทีมทำงานคู่ขนานกัน ภายในกรอบเวลา 60-90 วัน

- เหมาะเมื่อ: ความต้องการชัดเจน และขอบเขตโครงการจำกัด
- **ข้อเสีย:** ต้องใช้ทรัพยากรเยอะสำหรับโครงการใหญ่, ต้องการทีมที่มุ่งมั่นตามตารางเวลา, ไม่เหมาะกับโครงการที่มีความเสี่ยงทางเทคนิคสูงหรือใช้เทคโนโลยีใหม่

### จ) Spiral Model (แบบก้นหอย)
ผสาน iterative ของ prototyping กับความเป็นระบบของ linear model เข้าด้วยกัน แบ่งเป็นภาค (region): **customer communication, planning, risk analysis, engineering, construction & release, customer evaluation**

- **จุดเด่น:** เหมาะกับระบบขนาดใหญ่ และมีการวิเคราะห์ความเสี่ยง (risk analysis) อย่างเป็นระบบทุกรอบ
- **ข้อเสีย:** โน้มน้าวลูกค้าให้เชื่อว่าวิธีนี้ควบคุมได้ยาก เพราะเป็นโมเดลที่ค่อนข้างใหม่

### ฉ) Concurrent Model (แบบขนาน)
มองงานวิศวกรรมซอฟต์แวร์เป็น "สถานะ" (state) ต่างๆ ที่กิจกรรมหลายอย่าง (เช่น modeling, construction) เปลี่ยนสถานะพร้อมกันได้ เช่น "Under Development" → "Awaiting Changes" → "Under Review" → "Baselined" → "Done"

> **ตัวอย่าง:** ในระบบ client/server ทีม backend กับทีม frontend สามารถออกแบบและพัฒนาคอมโพเนนต์ของตัวเองไปพร้อมกันได้ ไม่ต้องรอกัน

## 2.5 The Unified Process (UP)

ลักษณะสำคัญ 4 อย่าง: **Use-case driven, Incremental & Iterative, Architecture-centric, Visual Modeling ด้วย UML**

5 ระยะของ UP:
1. **Inception** — ศึกษาความเป็นไปได้ (feasibility), ระบุฟีเจอร์และความต้องการเบื้องต้น
2. **Elaboration** — สร้าง use-case model, analysis model, design model
3. **Construction** — เขียนโค้ดและทดสอบ (initial operational capability)
4. **Transition** — ทดสอบแบบ beta และเตรียมเอกสารสนับสนุน (user manual)
5. **Production** — ติดตามการใช้งานจริง จัดการ defect report และ change request

> UP เน้นว่า Use Case คือศูนย์กลางที่เชื่อมทุกมุมมอง (Logical View, Implementation View, Process View, Deployment View) เข้าด้วยกัน — เรียกว่า "The Architect's Vision"

## 2.6 กิจกรรมร่ม (Umbrella Activities)

กิจกรรมที่ครอบคลุมตลอดทั้งวงจรชีวิตโครงการ ไม่ใช่แค่ช่วงใดช่วงหนึ่ง:
- การบริหารโครงการซอฟต์แวร์
- การทบทวนทางเทคนิคอย่างเป็นทางการ (formal technical reviews)
- การประกันคุณภาพซอฟต์แวร์ (SQA)
- การบริหารการปรับแต่งซอฟต์แวร์ (configuration management)
- การจัดการนำกลับมาใช้ใหม่ (reusability management)
- การบริหารความเสี่ยง (risk management)

## 2.7 CMMI (Capability Maturity Model Integration)

พัฒนาโดย Software Engineering Institute (SEI), Carnegie Mellon เป็นแนวทางปรับปรุงกระบวนการขององค์กร

**ระดับความสามารถ (Capability Levels) 0-5:**

| ระดับ | ชื่อ | ความหมายสั้นๆ |
|---|---|---|
| 0 | Incomplete | ไม่ได้ทำ หรือทำแค่บางส่วน |
| 1 | Performed | ทำได้ผลงานที่มีประโยชน์ แต่ยังไม่เสถียร |
| 2 | Managed | มีการวางแผน ควบคุม ติดตามในระดับโครงการ |
| 3 | Defined | ปรับแต่งจากมาตรฐานองค์กร |
| 4 | Quantitatively Managed | ควบคุมด้วยสถิติ/เชิงปริมาณ |
| 5 | Optimizing | ปรับปรุงต่อเนื่องจากความเข้าใจสาเหตุความแปรปรวน |

**ระดับวุฒิภาวะขององค์กร (Maturity Levels) 1-5** มีแนวคิดคล้ายกันแต่มองที่ระดับองค์กรทั้งหมด แทนที่จะมองแค่ process เดียว

> **ตัวอย่าง:** องค์กรระดับ Maturity 1 (Initial) มักส่งมอบงานได้ แต่งบและเวลาบานปลายบ่อย เพราะทำงานแบบ "ดับไฟ" เฉพาะหน้า ส่วนองค์กรระดับ 5 (Optimizing) จะใช้ข้อมูลเชิงสถิติมาปรับปรุงกระบวนการอย่างต่อเนื่อง

## สรุปจำง่าย

- Process คือวิธีการทำงาน ส่วน Product คือผลลัพธ์
- Waterfall เหมาะกับงานที่นิ่งและชัด แต่ไม่ยืดหยุ่น
- Prototyping ช่วยหาความต้องการเร็ว แต่ต้องระวังเอาต้นแบบไปใช้จริง
- UP เน้น use case และการพัฒนาแบบ iterative
- CMMI ใช้ดูระดับความพร้อมของกระบวนการและการปรับปรุงต่อเนื่อง
