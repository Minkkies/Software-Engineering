# บทที่ 3: วิศวกรรมความต้องการ (Requirements Engineering)

## 3.1 งานหลัก 7 อย่างของ Requirements Engineering

1. **Inception (การเริ่มต้น)** — ตั้งคำถามเพื่อเข้าใจปัญหาเบื้องต้น เช่น "ใครคือคนที่ต้องการวิธีแก้ปัญหานี้?", "ระบบจะสร้างประโยชน์ทางเศรษฐกิจอย่างไร?"
2. **Elicitation (การรวบรวมความต้องการ)** — ดึงความต้องการจากผู้มีส่วนได้ส่วนเสียทุกคน
3. **Elaboration (การขยายความ)** — สร้าง analysis model ที่ระบุข้อมูล ฟังก์ชัน และพฤติกรรม
4. **Negotiation (การเจรจาต่อรอง)** — ตกลงระบบที่ทั้งนักพัฒนาและลูกค้ายอมรับได้จริง
5. **Specification (การระบุสเปค)** — อาจเป็นเอกสาร, แบบจำลอง, สูตรคณิตศาสตร์, use-case, หรือ prototype
6. **Validation (การตรวจสอบความถูกต้อง)** — หาข้อผิดพลาด ความไม่สอดคล้อง ความต้องการที่ขัดแย้งกัน
7. **Requirements Management (การบริหารความต้องการ)** — ติดตามการเปลี่ยนแปลงของความต้องการตลอดโครงการ

> **ตัวอย่าง:** ทีมพัฒนาระบบ SafeHome (ระบบรักษาความปลอดภัยบ้าน) ต้อง **Inception** ถามเจ้าของบ้านว่าต้องการป้องกันอะไร แล้ว **Elicit** ความต้องการจากทั้งเจ้าของบ้านและช่างติดตั้งเซนเซอร์ จากนั้น **Elaborate** เป็น use-case model ก่อนจะ **Negotiate** ขอบเขตที่ทำได้จริงกับงบประมาณ

## 3.2 ทำไม Elicitation ถึงยาก?

3 ปัญหาหลัก:
- **ปัญหาเรื่องขอบเขต (Problems of scope)** — ไม่รู้ว่าระบบควรทำแค่ไหน
- **ปัญหาเรื่องความเข้าใจ (Problems of understanding)** — ลูกค้าเองก็อาจไม่รู้ว่าต้องการอะไรแน่ชัด
- **ปัญหาเรื่องความผันผวน (Problems of volatility)** — ความต้องการเปลี่ยนไปเรื่อยๆ ระหว่างทาง

## 3.3 การจัดประชุมรวบรวมความต้องการ (FAST meetings)

องค์ประกอบของการประชุม:
- มีทั้งวิศวกรซอฟต์แวร์และลูกค้าเข้าร่วม
- มีกฎการเตรียมตัวและการมีส่วนร่วมชัดเจน
- มี **facilitator** (ผู้ดำเนินการประชุม อาจเป็นลูกค้า นักพัฒนา หรือคนนอก) คอยควบคุม
- ใช้ **definition mechanism** เช่น กระดาษทำงาน กระดานไวท์บอร์ด หรือฟอรัมออนไลน์
- เป้าหมาย: ระบุปัญหา เสนอทางแก้ เจรจาต่อรอง และสรุปความต้องการเบื้องต้น

## 3.4 Quality Function Deployment (QFD)

แบ่งความต้องการเป็น 3 ประเภท:

| ประเภท | ความหมาย | ผลถ้าไม่มี |
|---|---|---|
| **Normal Requirement** | ความต้องการที่ลูกค้าพูดออกมาตรงๆ ในที่ประชุม | ถ้ามีครบ ลูกค้าพอใจ |
| **Expected Requirement** | ความต้องการโดยนัย ที่ลูกค้าไม่ได้พูดออกมาเพราะคิดว่า "มันต้องมีอยู่แล้ว" | ถ้าไม่มี ลูกค้าไม่พอใจอย่างมาก |
| **Exciting Requirement** | ฟีเจอร์ที่เกินความคาดหวังของลูกค้า | ถ้ามี ลูกค้าประทับใจเกินคาด |

> **ตัวอย่าง:** ระบบจองโรงแรมออนไลน์ — **Normal** คือ "ค้นหาห้องพักได้" (ลูกค้าขอตรงๆ), **Expected** คือ "เว็บไซต์ต้องปลอดภัย ข้อมูลบัตรเครดิตไม่รั่วไหล" (ไม่มีใครพูด แต่ต้องมี), **Exciting** คือ "ระบบแนะนำโรงแรมที่ตรงรสนิยมโดยอัตโนมัติ" (เกินคาด ทำให้ลูกค้าประทับใจ)

## 3.5 ผลผลิตจากขั้นตอน Elicitation

- คำชี้แจงความต้องการและความเป็นไปได้ (statement of need and feasibility)
- ขอบเขตของระบบที่ชัดเจน
- รายชื่อลูกค้า ผู้ใช้ และผู้มีส่วนได้ส่วนเสีย
- รายการความต้องการ (จัดตามฟังก์ชัน) พร้อมข้อจำกัดของโดเมน
- ชุด usage scenarios
- ต้นแบบ (prototypes) ถ้ามีการสร้าง

## 3.6 Use-Cases

Use-case คือชุดของสถานการณ์ผู้ใช้ (user scenario) ที่บรรยายจากมุมมองของ **actor** (คนหรืออุปกรณ์ที่มีปฏิสัมพันธ์กับระบบ)

คำถามสำคัญที่แต่ละ scenario ต้องตอบ:
- ใครคือ actor หลักและรอง?
- actor มีเป้าหมายอะไร?
- เงื่อนไขเบื้องต้น (precondition) คืออะไร?
- มีงานหลักอะไรบ้างที่ actor ทำ?
- มีความเป็นไปได้อื่น (extensions/variations) อะไรบ้าง?

> **ตัวอย่างจากสไลด์ (ระบบ SafeHome):**
> - Actor: **เจ้าของบ้าน (homeowner)** → ทำ use-case "เปิด/ปิดระบบ (Arms/disarms system)", "เข้าถึงระบบผ่านอินเทอร์เน็ต", "ปรับตั้งค่าเซนเซอร์"
> - Actor: **ผู้ดูแลระบบ (system administrator)** → ทำ use-case "ตอบสนองเหตุการณ์เตือนภัย (Responds to alarm event)", "จัดการข้อผิดพลาด"

## 3.7 การขยายความ (Elaboration) และ Analysis Model

หลังได้ use-case scenario แล้ว จะนำมา "แกะ" (parse) เพื่อสร้าง **Analysis Model** ซึ่งประกอบด้วย 4 องค์ประกอบ:

1. **Scenario-based elements** — functional (การประมวลผล) และ use-case (ปฏิสัมพันธ์ actor-ระบบ)
2. **Class-based elements** — คลาสที่นัยอยู่ในสถานการณ์ เช่น class `Sensor` ที่มี attribute (name, type, location) และ method (identify(), enable(), disable())
3. **Behavioral elements** — เช่น **State Diagram** ที่แสดงสถานะของระบบ

> **ตัวอย่าง State Diagram (เครื่องถ่ายเอกสาร):** เริ่มที่ "Initialization" → พร้อมใช้งาน "Subsystems Ready" → เมื่อกดคำสั่งคัดลอก เข้าสู่ "Making Copies" → ถ้ากระดาษติดจะเปลี่ยนไปที่ "Problem Diagnosis" → ถ้ากระดาษหมดจะไปที่ "Load Paper" — แต่ละสถานะมี entry action และ do-action ของตัวเอง

4. **Flow-oriented elements** — เช่น Data Flow Diagram (DFD)

## 3.8 การเจรจาความต้องการ

ขั้นตอน:
1. ระบุผู้มีส่วนได้ส่วนเสียหลัก (key stakeholders)
2. หา **win conditions** ของแต่ละฝ่าย (ซึ่งบางทีก็ไม่ชัดเจนตั้งแต่แรก)
3. เจรจาเพื่อให้ได้ชุดความต้องการที่นำไปสู่ผลลัพธ์แบบ **win-win**

## 3.9 การตรวจสอบความต้องการ

คำถามสำคัญที่ต้องถามทุกความต้องการ:
- สอดคล้องกับวัตถุประสงค์รวมของระบบหรือไม่?
- ระบุในระดับนามธรรมที่เหมาะสมหรือไม่ (ไม่ลงรายละเอียดทางเทคนิคเกินไปในช่วงนี้)?
- จำเป็นจริงหรือเป็นแค่ฟีเจอร์เสริม?
- มีขอบเขตชัดเจนและไม่กำกวมหรือไม่?
- มีการระบุแหล่งที่มา (attribution) หรือไม่ — ใครเป็นคนขอความต้องการนี้?
- ขัดแย้งกับความต้องการอื่นหรือไม่?
- ทำได้จริงในสภาพแวดล้อมทางเทคนิคที่มีหรือไม่?
- ทดสอบได้หรือไม่เมื่อ implement เสร็จแล้ว?

> **ตัวอย่าง:** ถ้ามีความต้องการว่า "ระบบต้องตอบสนองภายใน 0.001 วินาที" แต่ไม่มีแหล่งที่มาชัดเจนว่าใครขอ และไม่สามารถทดสอบได้จริงในงบประมาณที่มี — ความต้องการนี้จะไม่ผ่านการ validate

## 3.10 การบริหารความต้องการ

ทุกความต้องการจะถูก:
1. **Identification** — กำหนดรหัสเฉพาะ (unique identifier)
2. สร้าง **traceability table** 4-5 แบบ:
   - **Feature traceability table** — ความต้องการเชื่อมกับฟีเจอร์ที่ลูกค้าสังเกตเห็นได้อย่างไร
   - **Source traceability table** — ใครเป็นแหล่งที่มาของความต้องการนี้
   - **Dependency traceability table** — ความต้องการนี้เกี่ยวข้อง/ขึ้นกับความต้องการอื่นอย่างไร
   - **Subsystem traceability table** — จัดหมวดหมู่ตาม subsystem ที่ดูแล
   - **Interface traceability table** — ความต้องการนี้เกี่ยวข้องกับ interface ภายใน/ภายนอกอย่างไร

> **ทำไมต้องมี traceability table?** เพราะเวลาความต้องการหนึ่งเปลี่ยน เราจะได้รู้ทันทีว่ามันกระทบกับส่วนไหนของระบบบ้าง — เหมือนมี "แผนที่ผลกระทบ" ไว้ใช้ตอนต้องแก้ไขระบบ

## สรุปจำง่าย

- Requirements Engineering คือชุดงานที่เปลี่ยนความต้องการดิบให้เป็นสเปคที่ชัดและตรวจสอบได้
- Elicitation ยากเพราะ scope, understanding และ volatility
- Use case คือเครื่องมือหลักในการเก็บและสื่อสารความต้องการ
- Validation ต้องเช็คความถูกต้อง ความชัดเจน ความเป็นไปได้ และความทดสอบได้
- Traceability ช่วยให้ตามผลกระทบของการเปลี่ยนความต้องการได้
