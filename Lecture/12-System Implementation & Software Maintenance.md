# สรุป: System Implementation & Software Maintenance

## ส่วนที่ 1: System Implementation (การนำระบบไปใช้งาน)

### กิจกรรมหลัก 6 อย่าง
1. **Coding** – เขียนโค้ดตามข้อกำหนดการออกแบบเชิงกายภาพ
2. **Testing** – ทดสอบด้วยกลยุทธ์ต่าง ๆ (ทำคู่ขนานกับ coding ได้)
3. **Installation** – กระบวนการเปลี่ยนจากระบบเดิมเป็นระบบใหม่
4. **Documentation** – จัดทำเอกสารระบบและเอกสารผู้ใช้
5. **Training** – ฝึกอบรมผู้ใช้งาน
6. **Support** – ให้การสนับสนุนผู้ใช้ทั้งปัจจุบันและอนาคต

**วัตถุประสงค์:** แปลงข้อกำหนดการออกแบบให้เป็นซอฟต์แวร์ที่ใช้งานได้จริง พร้อมจัดทำเอกสารและให้ความช่วยเหลือผู้ใช้

### ผลลัพธ์ (Deliverables) ของแต่ละกิจกรรม
| กิจกรรม | ผลลัพธ์ |
|---|---|
| Coding | โค้ดโปรแกรม, เอกสารประกอบโปรแกรม |
| Testing | แผนการทดสอบ, ข้อมูลทดสอบ, ผลการทดสอบ |
| Installation | คู่มือผู้ใช้, แผนฝึกอบรม, แผนติดตั้ง/แปลงระบบ |

### การติดตั้งระบบ (Installation) – 4 แนวทาง
- **Direct Installation** – ปิดระบบเก่าแล้วเปิดระบบใหม่ทันที
- **Parallel Installation** – รันระบบเก่าและใหม่พร้อมกันจนมั่นใจ
- **Single Location Installation** – ทดลองใช้ที่ไซต์เดียวก่อนขยายผล
- **Phased Installation** – ติดตั้งทีละส่วนจนครบทั้งระบบ

**ปัจจัยที่ต้องพิจารณา:** การแปลงข้อมูล, การหยุดระบบตามแผน, รอบธุรกิจขององค์กร

### เอกสารระบบ (Documentation)
- **System Documentation** – รายละเอียดการออกแบบและการทำงานภายใน แบ่งเป็น
  - Internal Documentation (อยู่ในซอร์สโค้ด)
  - External Documentation (แผนภาพ เช่น data flow, ER diagram)
- **User Documentation** – วิธีใช้งานระบบสำหรับผู้ใช้ทั่วไป

### การฝึกอบรมผู้ใช้ (Training)
- **หัวข้อ:** การใช้ระบบ, แนวคิดคอมพิวเตอร์ทั่วไป, แนวคิดระบบสารสนเทศ, แนวคิดองค์กร, การจัดการระบบ, การติดตั้งระบบ
- **วิธีการ:** ผู้เชี่ยวชาญประจำ, การสอนด้วยคอมพิวเตอร์, หลักสูตรทางการ, ระบบช่วยเหลือในซอฟต์แวร์, บทเรียนแบบ tutorial, แหล่งภายนอก (เช่น vendor), และ **EPSS** (ระบบสนับสนุนการทำงานแบบฝังในซอฟต์แวร์)

### การสนับสนุนผู้ใช้ (Support)
- สำคัญมากต่อความพึงพอใจของผู้ใช้ (จากผลสำรวจ J.D. Power)
- สองรูปแบบหลัก: **Information Center** (ติดตั้ง ให้คำปรึกษา สาธิต) และ **Help Desk** (จุดติดต่อเดียวสำหรับปัญหา)

### ปัจจัยความสำเร็จของการนำระบบไปใช้
- ระดับการใช้งานระบบจริง
- ความพึงพอใจของผู้ใช้

### การปิดโครงการ (Project Close Down)
- ประเมินทีมงานและย้ายไปโครงการอื่น
- แจ้งผู้เกี่ยวข้องว่าโครงการเข้าสู่ช่วงบำรุงรักษา
- ทบทวนหลังโครงการ (post-project review)
- ปิดสัญญากับลูกค้าอย่างเป็นทางการ

## ส่วนที่ 2: Software Maintenance (การบำรุงรักษาซอฟต์แวร์)

### กิจกรรมหลัก 4 อย่าง
1. รับคำร้องขอบำรุงรักษา (Obtaining maintenance requests)
2. แปลงคำร้องขอเป็นการเปลี่ยนแปลง
3. ออกแบบการเปลี่ยนแปลง
4. ดำเนินการเปลี่ยนแปลง

**ผลลัพธ์:** ซอฟต์แวร์เวอร์ชันใหม่ พร้อมเอกสารออกแบบที่ปรับปรุงแล้ว

### ประเภทของการบำรุงรักษา
- **Corrective** – แก้ไขข้อผิดพลาดในระบบ
- **Adaptive** – ปรับให้เข้ากับความต้องการทางธุรกิจ/เทคโนโลยีที่เปลี่ยนไป
- **Perfective** – เพิ่มฟีเจอร์ใหม่หรือปรับปรุงประสิทธิภาพ
- **Preventive** – ป้องกันปัญหาที่อาจเกิดในอนาคต

### ต้นทุนการบำรุงรักษา
- องค์กรจำนวนมากใช้งบประมาณ IT **ถึง 80%** ไปกับการบำรุงรักษา
- ปัจจัยที่มีผลต่อความง่ายในการบำรุงรักษา: ข้อบกพร่องแฝง, จำนวนผู้ใช้ระบบ, คุณภาพเอกสาร, บุคลากร, เครื่องมือ, โครงสร้างโปรแกรมที่ดี

### การจัดการทีมบำรุงรักษา – 3 โครงสร้าง
- **Separate** – ทีมบำรุงรักษาแยกจากทีมพัฒนา
- **Combined** – ผู้พัฒนาทำหน้าที่บำรุงรักษาด้วย
- **Functional** – บุคลากรบำรุงรักษาสังกัดหน่วยธุรกิจนั้น ๆ

### ตัววัดประสิทธิผล
- จำนวนความล้มเหลว, ระยะเวลาระหว่างความล้มเหลวแต่ละครั้ง, ประเภทความล้มเหลว
- **MTBF (Mean Time Between Failures)** – ตัวชี้วัดคุณภาพระบบตามเวลา

### กระบวนการบำรุงรักษาซอฟต์แวร์ (Software Maintenance Process)
1. Modification Request (คำร้องขอเปลี่ยนแปลง)
2. Classification & Identification
3. Analysis
4. Design
5. Implementation
6. System Test
7. Acceptance Test
8. Delivery
(วนกลับไปเป็น Modification Request ใหม่ในรอบถัดไป)

### การควบคุมคำร้องขอบำรุงรักษา
- แบ่งประเภทคำร้อง: **Error, Adaptation, Enhancement**
- มี flowchart ที่พิจารณาความรุนแรง (severity) ของ error เพื่อจัดลำดับความสำคัญ (เช่น error รุนแรงมากจะได้ Top Priority) ก่อนนำเข้าคิวดำเนินการ
