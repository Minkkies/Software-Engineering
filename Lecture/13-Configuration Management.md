# Configuration Management (การจัดการคอนฟิกูเรชัน)
## 1. Configuration Management (CM) คืออะไร

**CM** คือการจัดการ "ผลิตภัณฑ์ที่เกิดจากการเปลี่ยนแปลงของระบบ" ซอฟต์แวร์ไม่เคยหยุดนิ่ง เมื่อมีการแก้ไขก็จะเกิด **เวอร์ชันใหม่** อยู่เสมอ เช่น

- เวอร์ชันสำหรับเครื่องหรือระบบปฏิบัติการต่างกัน
- เวอร์ชันที่มีฟังก์ชันการทำงานต่างกัน
- เวอร์ชันที่ปรับแต่งตามความต้องการของลูกค้าแต่ละราย

**ประเด็นสำคัญ**

- การเปลี่ยนแปลงระบบเป็น **งานของทีม** ไม่ใช่งานของคนใดคนหนึ่ง
- เป้าหมายของ CM คือ **ควบคุมต้นทุนและแรงงาน** ที่ใช้ในการเปลี่ยนแปลงระบบ

---

## 2. มาตรฐาน CM (CM Standards)

CM ควรอิงตามชุดมาตรฐานที่องค์กรใช้ร่วมกัน โดยมาตรฐานต้องกำหนดว่า

1. **ระบุ (identify)** รายการต่าง ๆ อย่างไร
2. **ควบคุม (control)** การเปลี่ยนแปลงอย่างไร
3. **จัดการ (manage)** เวอร์ชันใหม่อย่างไร

มาตรฐานอาจอ้างอิงจากมาตรฐานภายนอก เช่น **IEEE Standard for CM**

---

## 3. การวางแผน CM (CM Planning)

### สิ่งที่ต้องถูกจัดการ

ผลผลิตทุกอย่างของกระบวนการพัฒนาซอฟต์แวร์อาจต้องถูกจัดการ ได้แก่

- Specifications (ข้อกำหนด)
- Designs (การออกแบบ)
- Programs (โปรแกรม)
- Test data (ข้อมูลทดสอบ)
- User manuals (คู่มือผู้ใช้)

ระบบขนาดใหญ่อาจมีเอกสาร **หลายพันฉบับ** จึงต้องมีแผนที่ดี

### CM Plan ประกอบด้วย

| หัวข้อ | รายละเอียด |
|---|---|
| ประเภทเอกสาร | กำหนดประเภทเอกสารที่ต้องจัดการ และรูปแบบการตั้งชื่อ |
| ความรับผิดชอบ | ใครรับผิดชอบขั้นตอน CM และการสร้าง **baseline** |
| นโยบาย | นโยบายการควบคุมการเปลี่ยนแปลง (change control) และการจัดการเวอร์ชัน (version management) |
| บันทึก | ระเบียนข้อมูล CM ที่ต้องเก็บรักษา |
| เครื่องมือ | เครื่องมือที่ใช้ช่วยงาน CM และข้อจำกัดในการใช้ |
| ฐานข้อมูล | กำหนด CM database สำหรับบันทึกข้อมูลคอนฟิกูเรชัน |

> **Baseline** คือชุดของ configuration item ที่ผ่านการตรวจสอบและ "ตรึง" ไว้ เพื่อใช้เป็นจุดอ้างอิงในการพัฒนาต่อ

---

## 4. การระบุ Configuration Item (Configuration Item Identification)

- โครงการใหญ่สร้างเอกสารหลายพันฉบับ ทุกฉบับต้อง **ระบุตัวตนได้ไม่ซ้ำกัน**
- เอกสารบางส่วนต้องเก็บไว้ **ตลอดอายุของซอฟต์แวร์**
- ควรมี **รูปแบบการตั้งชื่อ (naming scheme)** ที่ทำให้เอกสารที่เกี่ยวข้องกันมีชื่อที่สัมพันธ์กัน

---

## 5. ฐานข้อมูลคอนฟิกูเรชัน (Configuration Database)

ข้อมูล CM ทั้งหมดควรเก็บไว้ในฐานข้อมูลเดียว และต้องตอบคำถามเกี่ยวกับคอนฟิกูเรชันได้ เช่น

- ใครถือเวอร์ชันหนึ่ง ๆ ของระบบอยู่?
- เวอร์ชันนี้ต้องการแพลตฟอร์มอะไร?
- ถ้าแก้ component X จะกระทบเวอร์ชันไหนบ้าง?
- เวอร์ชัน T มีรายงานข้อบกพร่อง (fault) กี่รายการ?

## 6. การจัดการการเปลี่ยนแปลง (Change Management)

ซอฟต์แวร์มีคำขอเปลี่ยนแปลงอย่างต่อเนื่อง จากหลายแหล่ง

- **ผู้ใช้** (users)
- **นักพัฒนา** (developers)
- **แรงผลักดันของตลาด** (market forces)

เป้าหมายคือ ให้การเปลี่ยนแปลงถูกนำไปใช้อย่าง **คุ้มค่าที่สุด**

### กระบวนการจัดการการเปลี่ยนแปลง (Pseudocode ในสไลด์)

```text
Request change by completing a change request form
Analyze change request
if change is valid then
    Assess how change might be implemented
    Assess change cost
    Submit request to change control board
    if change is accepted then
        repeat
            make changes to software
            submit changed software for quality approval
        until software quality is adequate
        create new system version
    else
        reject change request
else
    reject change request
```

**อธิบายเป็นขั้นตอน**

1. ผู้ขอกรอก **Change Request Form**
2. วิเคราะห์คำขอว่า **ถูกต้อง/สมเหตุสมผล** หรือไม่ ถ้าไม่ → ปฏิเสธ
3. ถ้าถูกต้อง → ประเมินวิธีทำและ **ต้นทุน**
4. ส่งให้ **Change Control Board (CCB)** ตัดสินใจ
5. ถ้า CCB ยอมรับ → แก้ซอฟต์แวร์ ส่ง QA ตรวจ วนซ้ำจนคุณภาพเพียงพอ → สร้างระบบเวอร์ชันใหม่
6. ถ้าไม่ยอมรับ → ปฏิเสธคำขอ

### แบบฟอร์มคำขอเปลี่ยนแปลง (Change Request Form)

- การออกแบบฟอร์มเป็นส่วนหนึ่งของ **CM planning**
- **ผู้ขอ (requestor)** กรอก: สิ่งที่ต้องการเปลี่ยน, ผู้เสนอ, เหตุผล, ความเร่งด่วน
- **ทีมบำรุงรักษาระบบ (maintenance staff)** กรอก: การประเมินการเปลี่ยนแปลง, การวิเคราะห์ผลกระทบ, ต้นทุน, ข้อเสนอแนะ

**ตัวอย่างในสไลด์ (Proteus/PCL-Tools, คำขอ 23/94)**

| ช่อง | ค่า |
|---|---|
| ผู้ขอ | I. Sommerville (1/12/98) |
| สิ่งที่ขอ | เมื่อเลือก component จากโครงสร้าง ให้แสดงชื่อไฟล์ที่เก็บ component นั้น |
| ผู้วิเคราะห์ | G. Dean (10/12/98) |
| Component ที่ได้รับผลกระทบ | Display-Icon.Select, Display-Icon.Display |
| Component ที่เกี่ยวข้อง | FileTable |
| การประเมิน | ทำได้ค่อนข้างง่าย เพราะมีตารางชื่อไฟล์อยู่แล้ว ต้องออกแบบและสร้างช่องแสดงผลเพิ่ม ไม่ต้องแก้ component ที่เกี่ยวข้อง |
| ความสำคัญ | ต่ำ (Low) |
| ประมาณการแรงงาน | 0.5 วัน |
| ส่งให้ CCB | 15/12/98 |
| CCB ตัดสิน | **ยอมรับ** (1/2/99) — ทำใน Release 2.1 |

### Change Control Board (CCB)

- เป็นกลุ่ม **ภายนอกโครงการ** ที่ตรวจสอบการเปลี่ยนแปลง
- ตัดสินจากมุม **กลยุทธ์และองค์กร** ว่าคุ้มค่าหรือไม่ **ไม่ใช่มุมทางเทคนิค**
- ต้อง **เป็นอิสระ** จากโครงการที่รับผิดชอบระบบ
- อาจมีตัวแทนจากทั้ง **ลูกค้า** และ **ผู้รับเหมา (contractor)**

## 7. การจัดการเวอร์ชันและรีลีส (Version and Release Management)

หน้าที่หลัก 3 อย่าง

1. คิดรูปแบบ **การระบุเวอร์ชัน** ของระบบ
2. **วางแผน** ว่าจะผลิตเวอร์ชันใหม่เมื่อไร
3. วางแผนและ **แจกจ่าย** รีลีสใหม่

### นิยามคำศัพท์

| คำ | ความหมาย |
|---|---|
| **Version** | ระบบที่ **ต่างกันในเชิงฟังก์ชัน** จากระบบอื่น |
| **Variant** | ระบบที่ **ฟังก์ชันเหมือนกัน** แต่ต่างกันในเชิง **non-functional** (เช่น ทำงานบนแพลตฟอร์มต่างกัน) |
| **Release** | ระบบที่ **แจกจ่ายให้ผู้ใช้ภายนอก** ทีมพัฒนา |

---

## 8. การระบุเวอร์ชัน (Version Identification)

ต้องมีวิธีระบุเวอร์ชันของ component ที่ **ไม่กำกวม** โดยมี 3 เทคนิคพื้นฐาน

### 8.1 Version numbering (การใช้หมายเลขเวอร์ชัน)

ใช้ตัวเลขกำกับ เช่น V1.0, V1.1, V1.2, V2.0 … และสามารถแตกกิ่งได้ เช่น V1.1a, V1.1b, V1.1.1

```text
V1.0 → V1.1 → V1.2 → V2.0 → V2.1 → V2.2
        ├─ V1.1a
        ├─ V1.1b
        └─ V1.1.1
```

เรียกโครงสร้างนี้ว่า **Version derivation structure** (โครงสร้างการสืบทอดเวอร์ชัน)

### 8.2 Attribute-based identification (ระบุด้วยแอตทริบิวต์)

- ผูก **แอตทริบิวต์** หลายค่าเข้ากับเวอร์ชัน การรวมกันของแอตทริบิวต์ใช้ระบุเวอร์ชันนั้น
- ตัวอย่างแอตทริบิวต์: Date, Creator, Programming Language, Customer, Status
- **ข้อดี:** ทำ **query** ได้ เช่น "หาเวอร์ชันล่าสุดที่เป็น Java"
- ตัวอย่าง: `AC3D (language = Java, platform = NT4, date = Jan 1999)`

### 8.3 Change-oriented identification (ระบุตามการเปลี่ยนแปลง)

- รวม **เวอร์ชัน** เข้ากับ **การเปลี่ยนแปลง** ที่ทำให้เกิดเวอร์ชันนั้น
- ใช้กับ **ระบบทั้งระบบ** ไม่ใช่ระดับ component
- แต่ละคำขอเปลี่ยนแปลงมี **change set** อธิบายสิ่งที่แก้เพื่อทำให้เกิดการเปลี่ยนแปลงนั้น
- นำ change set มาใช้ **ตามลำดับ** ในหลักการสามารถสร้างเวอร์ชันของระบบที่มีชุดการเปลี่ยนแปลงใด ๆ ก็ได้

## 9. การจัดการรีลีส (Release Management)

รีลีสต้องรวม

- การแก้ไขที่เกิดจาก **ข้อผิดพลาดที่ผู้ใช้พบ** และ **การเปลี่ยนแปลงของฮาร์ดแวร์**
- **ฟังก์ชันใหม่** ของระบบ

**Release planning** คือการตัดสินใจว่า **ควรออกเวอร์ชันเป็นรีลีสเมื่อไร**

### รีลีสมีอะไรบ้าง

รีลีสไม่ใช่แค่โปรแกรมที่รันได้ แต่อาจรวมถึง

- ไฟล์คอนฟิกที่กำหนดการตั้งค่าสำหรับแต่ละการติดตั้ง
- ไฟล์ข้อมูลที่ระบบต้องใช้
- โปรแกรมหรือ shell script สำหรับติดตั้งลงฮาร์ดแวร์เป้าหมาย
- เอกสารทั้งแบบอิเล็กทรอนิกส์และแบบกระดาษ
- บรรจุภัณฑ์และการประชาสัมพันธ์

ปัจจุบันมักแจกจ่ายบน CD-ROM หรือเป็นไฟล์ติดตั้งให้ดาวน์โหลดจากเว็บ

### ปัญหาของรีลีส (Release Problems)

- ลูกค้า **อาจไม่ต้องการรีลีสใหม่** เพราะพอใจระบบเดิม หรือไม่อยากได้ฟังก์ชันที่เพิ่มมา
- ผู้จัดการรีลีส **ต้องไม่สมมติว่าทุกรีลีสก่อนหน้าถูกติดตั้งแล้ว**
- ไฟล์ทั้งหมดที่ต้องใช้ใน รีลีสควร **สร้างขึ้นใหม่** ทุกครั้งที่ติดตั้งรีลีสใหม่

### การตัดสินใจออกรีลีส (Release Decision Making)

การเตรียมและแจกจ่ายรีลีสมี **ค่าใช้จ่ายสูง** จึงต้องพิจารณาปัจจัยต่าง ๆ

| ปัจจัย | คำอธิบาย |
|---|---|
| **คุณภาพทางเทคนิคของระบบ** | ถ้ามีข้อบกพร่องร้ายแรงที่กระทบผู้ใช้จำนวนมาก อาจต้องออก **fault repair release** ส่วนข้อบกพร่องเล็กน้อยแก้ด้วย **patch** (มักแจกผ่านอินเทอร์เน็ต) ที่ใช้กับรีลีสปัจจุบันได้ |
| **กฎข้อที่ 5 ของ Lehman** | ปริมาณฟังก์ชันที่เพิ่มในแต่ละรีลีส **ค่อนข้างคงที่** ดังนั้นถ้ารีลีสก่อนหน้ามีฟังก์ชันใหม่มาก อาจต้องตามด้วย **repair release** |
| **คู่แข่ง** | อาจต้องออกรีลีสใหม่เพราะมีผลิตภัณฑ์คู่แข่งวางตลาด |
| **ความต้องการทางการตลาด** | ฝ่ายการตลาดอาจสัญญาวันวางจำหน่ายไว้แล้ว |
| **ข้อเสนอเปลี่ยนแปลงของลูกค้า** | สำหรับระบบที่พัฒนาเฉพาะลูกค้า ลูกค้าอาจจ่ายเงินให้ทำการเปลี่ยนแปลงชุดหนึ่ง และคาดหวังรีลีสทันทีที่ทำเสร็จ |

### การสร้างรีลีส (Release Creation)

- รวบรวม **ไฟล์และเอกสารทั้งหมด** ที่ต้องใช้สร้างรีลีส
- เขียน **configuration description** สำหรับฮาร์ดแวร์ต่าง ๆ และเขียน **installation script**
- ต้อง **บันทึกอย่างละเอียด** ว่ารีลีสนั้นสร้างจากไฟล์ใดบ้าง เพื่อให้ **สร้างซ้ำ (re-create)** ได้เมื่อจำเป็น

## สรุปภาพรวม

```text
CM Standards ──► CM Plan ──► Configuration Items + Config Database
                                     │
                                     ▼
                     Change Management (Change Request → CCB)
                                     │
                                     ▼
              Version Management (numbering / attribute / change-oriented)
                                     │
                                     ▼
                      Release Management (planning → creation)
```

**หัวใจของบทนี้:** ซอฟต์แวร์เปลี่ยนแปลงตลอดเวลา จึงต้องมีมาตรฐาน แผน ฐานข้อมูล และกระบวนการควบคุมที่ชัดเจน เพื่อให้รู้ว่า **แต่ละเวอร์ชันคืออะไร เปลี่ยนไปเพราะอะไร และควรส่งมอบให้ผู้ใช้เมื่อไร**
