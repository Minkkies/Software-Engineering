# บทที่ 6: Architectural Design (การออกแบบสถาปัตยกรรมซอฟต์แวร์)
## 1. Software Architecture คืออะไร?

ลองนึกภาพว่าเรากำลังจะสร้างบ้านหลังใหญ่ ก่อนลงมือสร้างจริง เราต้องมี **แบบพิมพ์เขียว** ก่อนใช่ไหมครับ ว่าห้องไหนอยู่ตรงไหน เชื่อมต่อกับห้องอื่นอย่างไร

**Software Architecture** ก็เหมือนแบบพิมพ์เขียวของโปรแกรม คือ **โครงสร้าง** ของระบบ ซึ่งประกอบด้วย:
- **components (ส่วนประกอบ)** — เหมือนห้องต่าง ๆ ในบ้าน
- **คุณสมบัติที่มองเห็นได้จากภายนอก** ของแต่ละส่วนประกอบ
- **ความสัมพันธ์** ระหว่างส่วนประกอบเหล่านั้น — เหมือนประตูที่เชื่อมห้องต่อห้อง

### Architectural Design คือกระบวนการอะไร?
คือกระบวนการ **ระบุระบบย่อย (sub-systems)** ที่ประกอบกันเป็นระบบใหญ่ พร้อมทั้งวาง **กรอบการควบคุมและการสื่อสาร** ระหว่างระบบย่อยเหล่านั้น พูดง่าย ๆ คือ การวางโครงสร้างภาพรวมของซอฟต์แวร์ทั้งระบบนั่นเอง

---

## 2. ขั้นตอนของ Architectural Design (3 ขั้นตอนหลัก)

| ขั้นตอน | อธิบายง่าย ๆ |
|---|---|
| **1. System Structuring** | แตกระบบใหญ่ออกเป็น "ระบบย่อยหลัก ๆ" และดูว่าแต่ละระบบย่อยคุยกันอย่างไร |
| **2. Modular Decomposition** | เอาระบบย่อยแต่ละอันมาแตกต่อให้เป็น "โมดูล" ย่อยลงไปอีก |
| **3. Control Modelling** | สร้างแบบจำลองว่าใคร "สั่งการ" ใคร ระหว่างส่วนต่าง ๆ ของระบบ |

ให้จำง่าย ๆ ว่า: **แตกระบบ → แตกโมดูล → ดูว่าใครคุมใคร**

---

## 3. System Structuring (การจัดโครงสร้างระบบ)

- เป็นการแบ่งระบบใหญ่ให้กลายเป็นระบบย่อยที่ทำงานร่วมกัน (interacting sub-systems)
- นิยมแสดงผลด้วย **block diagram** (แผนภาพสี่เหลี่ยม) ที่แสดงภาพรวมโครงสร้างของระบบ
- นอกจากนี้ยังอาจมีโมเดลที่ละเอียดขึ้น เพื่อแสดงว่าระบบย่อยแชร์ข้อมูลกันอย่างไร กระจายตัวอย่างไร และเชื่อมต่อกันอย่างไร

### Architectural Styles (รูปแบบสถาปัตยกรรม)
เปรียบเหมือน "แบบบ้านสำเร็จรูป" ที่มีคนคิดไว้ให้แล้ว เราสามารถหยิบมาปรับใช้ได้ ช่วยให้ออกแบบง่ายขึ้น
- แต่ในความเป็นจริง **ระบบใหญ่ ๆ ส่วนมากไม่ได้ใช้แค่ style เดียว** มักผสมผสานกันหลายแบบ (heterogeneous)

---

## 4. รูปแบบสถาปัตยกรรมหลัก ๆ

### 4.1 Data-Centered Architecture (สถาปัตยกรรมเน้นข้อมูลเป็นศูนย์กลาง)

ลองนึกภาพ **คลังสินค้ากลาง** ที่ทุกแผนกวิ่งเข้ามาหยิบของ/เก็บของที่คลังนี้

- มี **data store** (ที่เก็บข้อมูล) อยู่ตรงกลาง
- ส่วนประกอบอื่น ๆ (client software) เข้ามา **อ่าน/เพิ่ม/ลบ/แก้ไข** ข้อมูลในนั้นบ่อย ๆ
- จุดเด่น: เราสามารถเปลี่ยนแปลง component เดิม หรือเพิ่ม client ใหม่ได้ โดยไม่กระทบ client อื่น เพราะแต่ละ client ทำงาน**อิสระ**จากกัน

#### Repository Model (โมเดลคลังข้อมูลกลาง)
การแชร์ข้อมูลระหว่างระบบย่อยทำได้ 2 แบบ:
1. **Shared data / Repository** — เก็บข้อมูลไว้ที่ฐานข้อมูลกลางที่เดียว ทุกระบบย่อยเข้าถึงได้
2. **แยกฐานข้อมูลของตัวเอง** — แต่ละระบบย่อยมีฐานข้อมูลของตัวเอง แล้วส่งข้อมูลถึงกันโดยตรง

> เมื่อข้อมูลมีปริมาณมาก มักนิยมใช้แบบ Repository (แบบที่ 1)

**ตัวอย่าง:** ระบบเครื่องมือ CASE tool ที่มี Project Repository อยู่ตรงกลาง แล้วมี Design editor, Program editor, Code generator, Report generator ฯลฯ ล้อมรอบ

**ข้อดี:**
- แชร์ข้อมูลปริมาณมากได้อย่างมีประสิทธิภาพ
- ระบบย่อยไม่ต้องสนใจว่าข้อมูลถูกสร้างขึ้นมาอย่างไร
- บริหารจัดการจากศูนย์กลางได้ (backup, security)
- โครงสร้างข้อมูลถูกเผยแพร่เป็น schema กลาง ทุกคนรู้ตรงกัน

**ข้อเสีย:**
- ทุกระบบย่อยต้อง "ตกลง" ใช้โมเดลข้อมูลเดียวกัน (มักต้องประนีประนอมกัน)
- การเปลี่ยนแปลงโครงสร้างข้อมูลทำได้ยากและมีค่าใช้จ่ายสูง
- ไม่มีพื้นที่ให้ทำนโยบายจัดการเฉพาะของแต่ละระบบ
- กระจาย (distribute) ระบบออกไปได้ยาก

---

### 4.2 Client-Server Architecture

เหมือน **ร้านอาหาร**: มีลูกค้า (client) หลายโต๊ะ สั่งอาหารไปที่ครัว (server) ต่าง ๆ กัน เช่น ครัวของหวาน ครัวเครื่องดื่ม

- เป็นโมเดลของระบบแบบกระจาย (distributed system)
- มี **server** หลายตัว ให้บริการเฉพาะทาง เช่น พิมพ์เอกสาร, จัดการข้อมูล
- มี **client** ที่เรียกใช้บริการเหล่านั้น
- เชื่อมกันผ่าน **เครือข่าย (network)**

**ตัวอย่าง:** ระบบห้องสมุดภาพยนตร์และรูปภาพ ที่มี Catalogue server, Video server, Picture server, Hypertext server แยกกัน แล้วให้ Client 1-4 เชื่อมต่อผ่านเครือข่ายความเร็วสูง

**ข้อดี:**
- กระจายข้อมูลได้ง่าย
- ใช้ประโยชน์จากระบบเครือข่ายได้ดี อาจใช้ฮาร์ดแวร์ที่ถูกกว่าได้
- เพิ่ม server ใหม่ หรืออัปเกรด server เดิมได้ง่าย

**ข้อเสีย:**
- ไม่มีโมเดลข้อมูลกลางร่วมกัน แต่ละระบบย่อยอาจจัดข้อมูลต่างกัน ทำให้แลกเปลี่ยนข้อมูลไม่มีประสิทธิภาพ
- แต่ละ server ต้องจัดการงานบริหารซ้ำซ้อนกันเอง
- ไม่มีทะเบียนกลางที่บอกว่ามี server/service อะไรบ้าง อาจหายากว่ามีบริการอะไรให้ใช้

---

### 4.3 Layered Architecture (สถาปัตยกรรมแบบเป็นชั้น)

ลองนึกภาพ **หัวหอม** ที่ปอกทีละชั้น หรือ **เค้กหลายชั้น**

- แบ่งระบบออกเป็นหลาย ๆ **ชั้น (layer)** โดยแต่ละชั้นทำงานที่ค่อย ๆ ใกล้กับ "ชุดคำสั่งเครื่อง (machine instruction)" มากขึ้นเรื่อย ๆ
- **ชั้นนอกสุด**: จัดการส่วนติดต่อผู้ใช้ (user interface)
- **ชั้นในสุด**: ทำหน้าที่เชื่อมกับระบบปฏิบัติการ (OS)
- **ชั้นกลาง**: ให้บริการ utility และฟังก์ชันของแอปพลิเคชัน

โครงสร้างตัวอย่าง (จากนอกไปใน):
```
user interface layer → application layer → utility layer → core layer
```

**ข้อดี:**
- เปลี่ยนแปลงและพกพา (portable) ได้ง่าย เพราะแต่ละชั้นแยกกันชัดเจน

**ข้อเสีย:**
- จัดระเบียบชั้นให้เหมาะสมทำได้ยาก
- ประสิทธิภาพอาจลดลง เพราะต้องส่งข้อความ (message) ผ่านหลาย interface กว่าจะถึงชั้นที่ต้องการ

---

### 4.4 คุณสมบัติของสถาปัตยกรรม (Architecture Attributes)

เวลาออกแบบ เราต้องคำนึงถึงคุณสมบัติต่อไปนี้:

| คุณสมบัติ | วิธีทำให้ได้คุณสมบัตินี้ |
|---|---|
| **Performance (ประสิทธิภาพ)** | จำกัดการสื่อสารระหว่างระบบย่อยให้น้อยที่สุด (localise operations) |
| **Security (ความปลอดภัย)** | ใช้สถาปัตยกรรมแบบชั้น โดยเก็บทรัพยากรสำคัญไว้ชั้นในสุด |
| **Safety (ความปลอดภัยเชิงระบบ)** | แยก component ที่เกี่ยวข้องกับความปลอดภัยออกจากส่วนอื่น |
| **Availability (ความพร้อมใช้งาน)** | มี component สำรอง (redundant) ไว้ในระบบ |
| **Maintainability (ความง่ายในการดูแลรักษา)** | ใช้ component ที่มีขนาดเล็ก เป็นอิสระในตัวเอง (fine-grain, self-contained) |

---

## 5. Sub-systems vs Modules

| | Sub-system | Module |
|---|---|---|
| นิยาม | เป็น "ระบบในตัวมันเอง" ทำงานได้อิสระ ไม่พึ่งพาบริการจากระบบย่อยอื่น | เป็น component ที่ให้บริการกับ component อื่น แต่ไม่นับเป็นระบบแยกต่างหาก |

พูดง่าย ๆ **Sub-system ใหญ่กว่า และอิสระกว่า Module**

---

## 6. Modular Decomposition (การแตกโมดูล)

หลังจากแตกเป็นระบบย่อยแล้ว ขั้นถัดไปคือแตกระบบย่อยให้เป็น "โมดูล" ย่อยลงไปอีก มี 2 โมเดลหลัก:

1. **Object Model** — แตกระบบเป็น "อ็อบเจกต์" ที่โต้ตอบกัน
2. **Data-flow Model (Pipeline Model)** — แตกระบบเป็นโมดูลที่ทำหน้าที่ "แปลงข้อมูลนำเข้าเป็นข้อมูลส่งออก"

> คำแนะนำ: ถ้าเป็นไปได้ ควรเลื่อนการตัดสินใจเรื่อง concurrency (การทำงานพร้อมกัน) ไว้จนกว่าจะเริ่ม implement โมดูลจริง ๆ

### 6.1 Object Model

- จัดโครงสร้างระบบให้เป็นชุดของ **object ที่เชื่อมต่อกันแบบหลวม ๆ (loosely coupled)** ผ่าน interface ที่ชัดเจน
- การแตกแบบ Object-Oriented จะเน้นระบุ **class ของอ็อบเจกต์**, **attribute**, และ **operation** ของแต่ละ class
- เมื่อนำไปพัฒนาจริง จะสร้าง object จาก class เหล่านี้ และใช้ control model ในการประสานงานระหว่าง object

**ตัวอย่าง:** ระบบประมวลผลใบแจ้งหนี้ (Invoice Processing) มี class เช่น `Invoice`, `Receipt`, `Payment`, `Customer` แต่ละ class มี attribute (เช่น invoice#, date, amount) และ operation (เช่น issue(), sendReminder(), acceptPayment(), sendReceipt())

### 6.2 Data-flow Architecture (Pipe and Filter)

ลองนึกภาพ **สายพานการผลิตในโรงงาน** ที่วัตถุดิบไหลผ่านแต่ละสถานี แล้วถูกแปรรูปไปเรื่อย ๆ จนออกมาเป็นสินค้าสำเร็จรูป

- ใช้เมื่อข้อมูลนำเข้าต้องถูก **แปลง (transform)** ผ่านชุดของ component เชิงคำนวณ จนได้ข้อมูลส่งออก
- **Pipe and Filter Pattern**: มี component เรียกว่า **filter** เชื่อมกันด้วย **pipe** ที่ส่งข้อมูลจาก filter หนึ่งไปยังอีก filter หนึ่ง
- แต่ละ filter ทำงาน **อิสระ** จาก filter ก่อนหน้าและถัดไป โดยรับข้อมูลรูปแบบหนึ่ง แล้วส่งออกข้อมูลอีกรูปแบบหนึ่งที่กำหนดไว้
- ถ้าการไหลของข้อมูลเป็นเส้นตรงเส้นเดียว (ไม่แตกสาขา) เรียกว่า **batch sequential** — รับข้อมูลเป็นชุด (batch) แล้วผ่าน filter ตามลำดับ

**ตัวอย่าง:** ระบบจ่ายเงิน ที่มีขั้นตอน: อ่านใบแจ้งหนี้ → หาว่าใบไหนถึงกำหนด → ระบุการจ่ายเงิน → ออกใบเสร็จ / ออกจดหมายเตือน

**ข้อดี:**
- นำ transformation กลับมาใช้ซ้ำ (reuse) ได้
- เข้าใจง่าย เพราะคนมักคิดงานเป็น "อินพุต → เอาต์พุต" อยู่แล้ว
- เพิ่ม transformation ใหม่เข้าไปในระบบทำได้ง่าย
- implement ได้ทั้งแบบ concurrent (พร้อมกัน) หรือ sequential (ตามลำดับ)

**ข้อเสีย:**
- ไม่เหมาะกับระบบที่ต้องโต้ตอบกับผู้ใช้แบบ interactive
- ทุก transformation ต้องใช้ "รูปแบบข้อมูลร่วมกัน" ที่ตัวอื่นเข้าใจได้
- ประสิทธิภาพอาจลดลงถ้ามีการประมวลผลข้อมูลซ้ำ ๆ

## 7. Control Models (โมเดลการควบคุม)

แตกต่างจากโมเดลการแตกระบบ (decomposition) ตรงที่ Control Model จะสนใจว่า **"ใครสั่งใคร"** ระหว่างระบบย่อย มี 2 แบบหลัก:

### 7.1 Centralised Control (การควบคุมแบบรวมศูนย์)
มีระบบย่อยหนึ่งตัวรับผิดชอบควบคุมทั้งหมด สั่ง start/stop ระบบย่อยอื่น ๆ แบ่งเป็น 2 โมเดลย่อย:

- **Call-return Model** — เหมือนต้นไม้ของฟังก์ชัน (subroutine hierarchy) ควบคุมเริ่มจากบนลงล่าง เหมาะกับระบบที่ทำงานตามลำดับ (sequential)
  - **Call and Return Architecture**: มี main program เรียกใช้ component ต่าง ๆ ซึ่ง component เหล่านั้นอาจเรียก component อื่นต่อไปอีก (เหมือนต้นไม้)
  - **Remote Procedure Call (RPC)**: เหมือนกันแต่ component กระจายอยู่คนละเครื่องในเครือข่าย

- **Manager Model** — เหมาะกับระบบที่ทำงานพร้อมกัน (concurrent) โดยมี component หนึ่งตัวควบคุมการ start/stop/ประสานงาน process อื่น ๆ (ถ้าเป็นระบบ sequential ก็ implement ได้ด้วย case statement)
  - **ตัวอย่าง Real-time system control**: มี System controller เป็นศูนย์กลาง เชื่อมกับ User interface, Fault handler, Computation processes, Sensor processes, Actuator processes

### 7.2 Event-based Control (การควบคุมตามเหตุการณ์)
ระบบย่อยแต่ละตัวตอบสนองต่อ **เหตุการณ์ (event)** ที่เกิดขึ้นจากภายนอก โดยที่ **จังหวะเวลา** ของ event นั้นไม่ได้อยู่ในการควบคุมของระบบย่อยเลย มี 2 แบบ:

#### ก) Broadcast Model
- event ถูก **กระจาย (broadcast)** ไปยังทุกระบบย่อย ใครจัดการ event นั้นได้ก็จัดการไป
- ระบบย่อยแต่ละตัว **ลงทะเบียน (register)** ความสนใจใน event ที่ตัวเองสนใจไว้ล่วงหน้า
- นโยบายการควบคุมไม่ได้ฝังอยู่ใน event/message handler — ระบบย่อยเป็นคนตัดสินใจเองว่าสนใจ event ไหน
- ข้อควรระวัง: ระบบย่อยที่ส่ง event ไม่รู้ว่า event ของตัวเองจะถูกจัดการหรือเมื่อไหร่
- มีประโยชน์มากในการรวมระบบย่อยที่อยู่คนละเครื่องในเครือข่ายเข้าด้วยกัน

#### ข) Interrupt-driven Model
- ใช้ในระบบ **real-time** ที่ต้องการการตอบสนองเร็วมากต่อเหตุการณ์
- มี "ชนิดของ interrupt (interrupt type)" ที่กำหนดไว้ล่วงหน้า แต่ละชนิดมี handler ของตัวเอง
- แต่ละชนิดผูกกับตำแหน่งหน่วยความจำ (memory location) และมี hardware switch คอยโอนการควบคุมไปยัง handler ที่ถูกต้อง
- ข้อดี: ตอบสนองได้เร็วมาก
- ข้อเสีย: เขียนโปรแกรมซับซ้อน และตรวจสอบความถูกต้อง (validate) ได้ยาก

## 8. สรุปภาพรวมทั้งหมด (Quick Recap)

```
Architectural Design
│
├── ขั้นตอน: System Structuring → Modular Decomposition → Control Modelling
│
├── Architectural Styles (รูปแบบโครงสร้างระบบย่อย)
│     ├── Data-Centered (มี data store กลาง) → Repository Model
│     ├── Client-Server (server ให้บริการ, client เรียกใช้)
│     └── Layered (แบ่งเป็นชั้น ๆ จากนอกสุดถึงในสุด)
│
├── Modular Decomposition (แตกระบบย่อยเป็นโมดูล)
│     ├── Object Model (แตกเป็น object/class)
│     └── Data-flow Model / Pipe & Filter (แตกเป็นสายการแปลงข้อมูล)
│
└── Control Models (ใครสั่งใคร)
      ├── Centralised: Call-return / Manager Model
      └── Event-based: Broadcast / Interrupt-driven
```

**เคล็ดลับในการจำ:** ให้ลองจับคู่แต่ละสถาปัตยกรรมกับสถานการณ์ในชีวิตจริง เช่น
- Data-Centered = คลังสินค้ากลาง
- Client-Server = ร้านอาหารที่มีครัวหลายแผนก
- Layered = หัวหอมที่ปอกทีละชั้น
- Pipe and Filter = สายพานโรงงาน
- Broadcast = ประกาศเสียงตามสาย ใครสนใจก็ฟัง
- Interrupt-driven = สัญญาณเตือนไฟไหม้ที่ต้องตอบสนองทันที
